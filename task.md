# Практика: HTTP-сервис для управления задачами

**Статус:** выполнено. Все этапы плана и итоговые проверки завершены.

## 1. Цель

Самостоятельно с нуля разработать на Go HTTP-сервис для управления задачами (todos). Сервис должен хранить данные в памяти, принимать и возвращать JSON, корректно обрабатывать ошибки и оставаться безопасным при одновременных запросах.

Работа должна закрепить:

- моделирование данных с помощью структур;
- применение интерфейсов для разделения HTTP-слоя и хранилища;
- создание REST API средствами стандартной библиотеки Go;
- кодирование и декодирование JSON;
- создание, оборачивание и распознавание ошибок;
- безопасную конкурентную работу с общими данными;
- тестирование HTTP-обработчиков;
- корректную остановку HTTP-сервера.

## 2. Что считаем заданием

В исходном документе приведены объяснения и готовый пример реализации. Они не являются кодом, который нужно перенести в проект. Из документа берём только функциональные требования и изучаемые технические приёмы.

В собственную реализацию входят:

1. CRUD API для задач.
2. In-memory хранилище.
3. JSON-запросы и ответы.
4. Валидация входных данных и HTTP-ошибки.
5. Потокобезопасность хранилища.
6. Фильтрация списка по статусу выполнения.
7. Graceful shutdown по сигналу завершения.
8. Автоматические тесты.

## 3. Функциональные требования

### 3.1. Модель задачи

Задача содержит:

- `id` — целочисленный идентификатор, назначаемый сервером;
- `title` — обязательное непустое название;
- `description` — необязательное описание;
- `done` — признак выполнения;
- `created_at` — время создания, назначаемое сервером.

Клиент не должен управлять `id` и `created_at`: при создании и обновлении сервер устанавливает или сохраняет эти значения самостоятельно.

### 3.2. HTTP API

| Метод | Путь | Назначение | Успешный статус |
| --- | --- | --- | --- |
| `GET` | `/tasks` | Получить все задачи | `200 OK` |
| `GET` | `/tasks/{id}` | Получить задачу по ID | `200 OK` |
| `POST` | `/tasks` | Создать задачу | `201 Created` |
| `PUT` | `/tasks/{id}` | Полностью обновить задачу | `200 OK` |
| `DELETE` | `/tasks/{id}` | Удалить задачу | `204 No Content` |

`GET /tasks` дополнительно поддерживает фильтр:

- `GET /tasks?done=true` — только выполненные задачи;
- `GET /tasks?done=false` — только невыполненные задачи.

Для списка без результатов возвращается пустой JSON-массив `[]`, а не `null`.

### 3.3. Ошибки и валидация

Сервис должен возвращать ошибки в едином JSON-формате:

```json
{"error":"описание ошибки"}
```

Минимальные случаи:

| Ситуация | Статус |
| --- | --- |
| Некорректный JSON | `400 Bad Request` |
| Пустой или состоящий из пробелов `title` | `400 Bad Request` |
| Некорректный ID в пути | `400 Bad Request` |
| Некорректное значение параметра `done` | `400 Bad Request` |
| Задача не существует | `404 Not Found` |
| Путь не существует | `404 Not Found` |
| Путь существует, но метод не поддерживается | `405 Method Not Allowed` |
| Непредвиденная внутренняя ошибка | `500 Internal Server Error` |

Во внутренних ошибках должен сохраняться контекст, а проверка известных причин должна работать через цепочку ошибок. Технические подробности внутренней ошибки не должны попадать клиенту.

### 3.4. Хранилище

Хранилище должно:

- предоставлять операции получения списка, получения по ID, создания, обновления и удаления;
- быть доступно HTTP-слою через небольшой интерфейс;
- хранить задачи в памяти;
- назначать уникальные возрастающие ID;
- сохранять исходное время создания при обновлении;
- безопасно обслуживать одновременные чтения и записи;
- возвращать распознаваемую ошибку, если задача не найдена.

Порядок задач в `GET /tasks` нужно сделать детерминированным, например по возрастанию ID. Это не сформулировано явно в исходном материале, но устраняет случайный порядок обхода `map` и делает API и тесты предсказуемыми.

### 3.5. Запуск и остановка

Сервис должен:

- запускаться на настраиваемом адресе с разумным значением по умолчанию, например `:8080`;
- логировать запуск и завершение работы;
- принимать `SIGINT` и `SIGTERM`;
- прекращать приём новых запросов и ждать завершения текущих запросов в пределах заданного тайм-аута;
- корректно отличать штатное закрытие сервера от ошибки запуска или работы.

## 4. Технические условия

- Язык: Go.
- HTTP: стандартный пакет `net/http`, без стороннего веб-фреймворка.
- JSON: стандартный пакет `encoding/json`.
- Хранение: только в памяти; база данных и файловая персистентность не требуются.
- Конкурентный доступ к данным должен быть синхронизирован.
- HTTP-слой не должен зависеть от конкретного типа in-memory хранилища.
- Для проверки HTTP использовать `net/http/httptest`.
- Проект должен проходить форматирование, статическую проверку, обычные тесты и тесты с race detector.

Размещение всего кода в одном файле из примера не является обязательным требованием. Структуру проекта определяем самостоятельно и усложняем только тогда, когда это улучшает понятность или тестируемость.

## 5. Что не входит в задачу

- база данных и сохранение задач после перезапуска;
- авторизация и пользователи;
- пагинация, поиск и сортировка по произвольным полям;
- частичное обновление через `PATCH`;
- веб-интерфейс;
- Docker, деплой и облачная инфраструктура;
- копирование готового решения из исходного документа.

## 8. Формат совместной работы

Основные учебные части студент пишет самостоятельно. Повторяющуюся HTTP-обвязку и объёмные тестовые сценарии по договорённости может реализовать помощник. Помощник:

- уточняет ожидаемое поведение до написания кода;
- подсказывает направление и задаёт наводящие вопросы;
- не выдаёт полную реализацию учебной части без отдельной просьбы;
- помогает составлять тесты до или сразу после реализации;
- проверяет код, объясняет ошибки и предлагает небольшой следующий шаг;
- следит, чтобы решения оставались понятными, а не только проходили тесты.
